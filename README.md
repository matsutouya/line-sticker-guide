この文書だけで、LINE Creators Market向けの「動くスタンプ(APNG)」を規格エラーなしで作れる。

Claude Code固有のツール名は一切使っていない。ブラウザ操作・ターミナル実行・Python実行ができるAI(Grokを含む)であれば、この手順をそのまま実行すればよい。

## 1. なぜこの手順が重要か

LINEの公式ガイドライン(https://creator.line.me/ja/guideline/animationsticker/)には数値の上限は書いてある。

しかし、**アップロードが通るかどうかを実際に左右する条件の一部は、ガイドラインに書かれていない**。

エラーメッセージも「Error」としか出ず、赤いバッジをクリックして初めて理由が分かる。

ここで試行錯誤すると、1枚あたり何度もの往復が発生する。

だから、最初から「通ることが分かっている作り方」で作ることに価値がある。

| 背景 | 透過必須 |

**基本は24個セットで作る**。8や16は、試作や一部だけ直すときに限る。最初から24個分のポーズ一覧を作り、24個完成させてからzip化する。ファイル名は2桁ゼロ埋め(`01`〜`24`)。

## 3. 実機検証でしか分からない落とし穴(ここが本題)

ガイドラインの数値を全部満たしていても、次の3つを踏むと「Error」表示になる。しかも理由は赤いバッジをクリックしないと出てこない。

### 3-1. 再生時間は1／2／3／4秒に"ぴったり"合わせる

「4秒以内」ではなく離散値の判定になっている。3.996秒や4.004秒のような端数は、数値上は「4秒以内」でも弾かれる。

**対策＝フレーム数は選んだ合計再生時間を割り切れる枚数(5・8・10・16・20)から選び、1コマの長さを全コマ完全に同じ値(合計時間÷フレーム数)にする**。端数を一切作らない。

**合計再生時間はデフォルトで2000ms(2秒)にする**(2026-08-20裁定)。以前は4000ms(4秒)を既定にしていたが、フレーム数が少ないポーズ(16枚など)で4秒だと動きが間延びして「カクカクしている」「遅い」と感じられたため、2秒を標準に変更した。5・8・10・16・20はいずれも2000msを割り切れるので、フレーム数の選び方自体は変わらない。ゆったりした動き(寝る・伸びをするなど)で2秒だと忙しなく感じる場合だけ、4000msを個別に選んでよい。

### 3-2. ループ回数は1〜4を明示する。0(無限ループ)は不可

さらに、**ループ回数×1コマ分の再生時間、の掛け算がLINE側の判定に影響している可能性が高い**。4秒のアニメを`loop=4`(ループ4回)で作ると「4秒×4回=16秒」と読まれて弾かれ続けた例がある。秒数だけ何度直しても変わらず、`loop=1`に変えて初めて通った。

**対策＝最初から`loop=1`で作る**。ループ回数の上限が4だからといって4を選ばない。

### 3-3. Pillow(PIL)は隣接する2コマが完全に同じ絵だと勝手に1コマへ統合する

これで「5枚のつもりが実は4枚で規格違反」という事故が起きる。原因は2パターンある。

- 2枚のキーフレームをA,B,A,B…と交互配置した後に枚数を間引くと、間引く間隔が元の交互周期(2)の倍数のとき、全コマが同じ絵になる(エイリアシング)。**整数比で割り切れる間引き方を避ける**。
- sin波などの周期関数でフレームを作るとき、フレーム数Nが周波数の係数の約数だと同じ理由で全コマ同一になる(例: `sin(10*ph)`をN=5やN=10でサンプリングすると常にゼロになる)。**Nは周波数の約数にしない**。

**対策＝保存する直前に、全ての隣接フレームのペアがpixel-identicalでないか必ず検証する**。1つでも一致していたら、そのペアの片方を作り直すか配置を変える。

### 3-4. コマごとに再生時間を変えるのはやめる(調査済みの誤ったリード)

「ためのあるお辞儀だから最初と最後のコマだけ長くしたい」のように、コマごとに再生時間を変えたくなることがある。

過去の制作でこれを試したところ(例: 666ms/670ms混在)、Pillowが保存時にPNGの`delay_num`/`delay_den`をコマごとに個別で約分するため、同じファイル内で分母がバラバラになる事象が発生した。

検証の結果、この分母のバラつき自体が直接のエラー原因ではないと分かっている。ただし、原因調査を難しくする余計な変数になるだけで得るものがない。

**最初から全コマ同じ長さ(合計再生時間÷フレーム数。デフォルトは2000÷フレーム数)にして、この変数自体を作らないこと**。動きに緩急をつけたいときは、再生時間ではなくコマの中身(ポーズの変化量)側で表現する。

### 3-5. 動画生成AIは、動きが大きい・感情が動くカットで絵柄を勝手に汚す(2026-08-20判明)

`validate_line_sticker()`と`check_ghosting()`は規格違反(サイズ・フレーム数・再生時間・残像)しか検出できない。**キャラクターデザイン自体が動画生成の途中で壊れる事故は、この2つのチェックを通っても平気ですり抜ける**。ねこ24個セットの制作で、ほぼ全ポーズでこの種の事故が起きた。

具体的に起きたパターンは2つ。

- **頬にピンクのチーク(赤み)が新しく描き足される**。元絵に無い色要素で、特に「うなずく」「お辞儀する」「振り向く」のような感情が動きそうな動作名を渡すと起きやすい。表情も釣られて笑顔・驚き顔・あくび顔に変わることが多い
- **肉球・前足の内側の毛が、動きが激しい場面(毛が逆立つ・跳ねる・走る)で赤黒い/血のような濃い赤に変色する**。耳の内側と同じ薄いピンクのはずが、動きのピーク付近だけ別の色になる

どちらも、動画の**前半〜中盤は正常で、後半(動きが最大化する・感情が乗る場面)から崩れ始める**という共通点がある。1コマ目と最終コマだけ確認すると見逃しやすい。

**対策**

1. 動画生成の依頼文に、動作の説明とは別に次を毎回明記する。「頬の赤み・ピンクのチークなど元画像に無い新しい色要素は絶対に描き足さないこと」「口・眉・ひげの形は完全固定、表情は驚き顔・あくび顔・笑顔に絶対にしないこと」「肉球・前足内側の毛の色は耳の内側と同じ薄いピンクのまま固定し、赤黒い色や臙脂色には絶対に変色させないこと」
2. **1コマ目と最終コマだけでなく、動画全体から最低6〜8箇所を切り出して目視確認する**。崩れは中盤以降にだけ出ることが多いため
3. 崩れが動画の終盤だけに出る場合、動きの内容自体は正しいことが多いので、崩れる前の時間で動画をトリムしてから`build_from_video.py`に渡せば作り直しを避けられる
4. それでも崩れる場合は、動きの激しさ(可動域の大きさ)を少し抑えてでも、絵柄の正確さを優先する。動きの大きさと絵柄の正確さがトレードオフになったときは、絵柄を優先する
5. 完成後、`validate_line_sticker()`と`check_ghosting()`が両方空リストでも、**必ず全コマを並べたコンタクトシートを作ってbase.jpgと目視で見比べる**。この2関数だけでは絵柄の汚染を検出できない

### 3-6. 崩れは動画生成より前、開始ポーズの静止画を描き起こす時点で入る(2026-08-21判明)

3-5は動画生成中に絵柄が汚れる話だった。それとは別に、**5-1で開始ポーズの静止画を描き起こす時点で、そもそも別のキャラクターが出来上がる**事故がある。動画生成はその静止画を忠実に動かすので、以降のコマは最後まで「別キャラのまま一貫して」正常に見える。3-5の対策(中盤・終盤の切り出し確認)では検出できない。

ハムスター24個セットの11番で実際に起きた。1回の生成で次が同時に外れた。

- 輪郭線が細く薄くなった
- 元絵に無い細長いヒゲが描き足された
- お腹の柄が、角のある雲形からただの楕円になった
- 尻尾が消えた
- 口が小さくなり、元絵の大きな舌が別物になった
- 体型が横に丸い形から縦長になった

`validate_line_sticker()`も`check_ghosting()`も空リストを返した。コマ同士は完全に一貫しているため、残像も規格違反も出ない。**規格チェックはキャラクターの同一性を一切見ていない**。

さらに悪いことに、この崩れ方は生成のたびに違う。1個ずつ描き起こして24個作ると、24通りに違うキャラクターが並ぶ。1個単位で見ると気づきにくく、セットとして並べて初めて分かる。

**対策＝キャラクターの照合項目を先に文章で決めておき、動画生成に進む前に静止画の段階で照合する関所を置く。**

1. `base.jpg`を見て、そのキャラクターを他と区別している特徴を8個前後、箇条書きの文章にする(輪郭線の太さと色・頬の毛かヒゲか・柄の形・尻尾の有無と太さ・耳の形と縁取り・目の形とハイライトの数・口と舌・体型の縦横比、など)。絵を見せるだけでは伝わらないので必ず文章にする
2. 開始ポーズの静止画を描き起こしたら、**動画生成に進む前に**その静止画と`base.jpg`を左右に並べた比較画像を作り、1項目ずつ照合する
3. 1つでも外れていたら、外れた項目を名指しして描き直す。動画生成には進まない
4. 顔のアップなど、構図の都合で写らない項目(尻尾など)は照合対象から外してよい。外したことを記録に残す
5. 描き起こした静止画は必ずファイルとして保存する。保存し忘れると、崩れがどの工程で入ったのかを後から特定できない

同じセットの19番・04番は、この照合を行った(あるいは生成をやり直した)結果、8項目すべてを保った。**工程自体は正しい結果を出せる。足りないのは、何をもって同じキャラクターとするかを文章にしておくこと**。

### 3-7. 輪郭の外側に不透明な白いフチ(ハロー)が残る(2026-08-21判明)

動画生成AIは、キャラクターの足元や体の周りに柔らかい影を描くことが多い。この影は`remove_white_bg()`のしきい値(全チャンネル>240)を下回るため透過されず、**輪郭線の外側に不透明な白い縁として残る**。

`check_ghosting()`は中間アルファ値の比率しか見ていないので、完全に不透明なこのフチを検出できない。`validate_line_sticker()`も当然通る。再生すると、コマによって輪郭の外に白い縁が出たり消えたりしてちらつく。

ハムスター15番で、1コマに283画素残った状態で規格チェックが両方とも空リストを返した。合格した他のスタンプは全コマ合計でも14画素以下だったので、桁で違う。

**検出のしかた**＝透明画素から3画素以内にある、不透明(alpha>200)で非常に明るく(最小チャンネル>235)彩度の無い(最大-最小<12)画素を数える。1コマで60画素を超えたら疑う。

```python
def check_white_fringe(path, per_frame_limit=60):
    from scipy import ndimage
    im = Image.open(path)
    n = im.n_frames if getattr(im, 'is_animated', False) else 1
    warnings = []
    for i in range(n):
        im.seek(i)
        arr = np.asarray(im.convert('RGBA'))
        alpha, rgb = arr[:, :, 3], arr[:, :, :3].astype(int)
        whiteish = (alpha > 200) & (rgb.min(-1) > 235) & ((rgb.max(-1) - rgb.min(-1)) < 12)
        edge = ndimage.binary_dilation(alpha < 30, iterations=3) & whiteish
        if int(edge.sum()) > per_frame_limit:
            warnings.append(f'フレーム{i}: 外周に不透明な白いフチ{int(edge.sum())}画素')
    return warnings
```

**やってはいけない直し方が2つある。どちらも実際に試して失敗した。**

1. **`remove_white_bg()`のしきい値を緩める**。影(238,219,202)とお腹のクリーム色(249,231,207)は色が近すぎて分離できない。緩めるとお腹まで透過する
2. **「濃い輪郭線を壁にして、背景から線を越えずに到達できる画素を消す」を、歯止めなしで書くこと**。顔アップなど体が画面端で切れている構図では輪郭が閉じていないため、そこから浸水して明るい毛とお腹を全部たどり、キャラクターが輪郭線だけになる。(この方式自体は、安全装置を2つ付ければ使える。3-8を見ること)

**通った直し方＝範囲を絞って消す。** フチは輪郭のすぐ外側の細い帯でしかないので、上の検出条件に当てはまる画素だけを透過にする。お腹のクリームは最小チャンネルが207で「>235」の条件を満たさないため、色の側で最初から除外される。

フチが3画素より厚い箇所は1回では取り切れない。外側から1層ずつ剥がれるので、変化がほぼ止まるまで(実測で4〜5周)繰り返す。

```python
def strip_frame(arr, near=3, min_ch=235, max_sat=12, alpha_bg=30):
    from scipy import ndimage
    alpha, rgb = arr[:, :, 3], arr[:, :, :3].astype(int)
    transparent = alpha < alpha_bg
    near_bg = ndimage.binary_dilation(transparent, iterations=near)
    whiteish = (rgb.min(-1) > min_ch) & ((rgb.max(-1) - rgb.min(-1)) < max_sat)
    fringe = near_bg & whiteish & ~transparent
    n = int(fringe.sum())
    if n:
        arr = arr.copy()
        a = arr[:, :, 3]; a[fringe] = 0; arr[:, :, 3] = a
    return arr, n

# 全コマに対して、1周の除去数が10画素以下になるまで最大8周繰り返してから保存する
```

この後処理は`build_from_video.py`の直後に毎回かける。かけ直しても、条件に当てはまる画素が無ければ何も起きないので安全。

なお、この後処理で透過を増やすと画像の実効サイズが変わることがある。保存前に`validate_line_sticker()`を再実行し、270px条件を満たしたままか確認すること。

### 3-8. 影には白い版とベージュの版があり、後者は後処理では消せない(2026-08-21判明)

3-7で消せるのは白いフチだけ。**ベージュの影(実測で約232,219,206)は最小チャンネルが206しかないので、3-7の条件(最小チャンネル>235)に引っかからず残る**。白背景のコンタクトシートでは見えず、彩度の高い背景に置いて初めて分かる。

3-7と同じ「範囲を絞って消す」を色の条件を緩めて適用してはいけない。ベージュの影(232,219,206)とお腹のクリーム(249,231,207)は色がほぼ同じで、色では分離できない。距離で絞る手も、体が画面端で切れている構図では体の断面が透明部分と隣り合うため、そこからクリームまで削れる。実際に15番と24番で試して、頬とお腹が食われた。

**通る直し方＝濃い輪郭線を壁にする方式に、安全装置を2つ付ける。** 3-7で「歯止めなしでやるな」と書いた方式そのものだが、次の2つを付けると成立する。どちらか一方でも欠けると壊れる。

1. **消す対象を明るい画素(最小チャンネル>180)に限る。** これが無いと、到達できる画素を明るさに関係なく全部消すことになり、中間色の茶色い毛まで食う。実際にこの条件を落とした版を書いて、キャラクターが輪郭線だけになった
2. **1コマで不透明画素の8%を超えて消えるなら、そのファイルは処理せず中断する。** 輪郭が閉じていない構図では浸水して大量に消えるので、割合を見れば自動で弾ける

この2つがあると、**構図を人が判断しなくても、通るときだけ通る**。全ファイルにかけてよい。実測では、全身が収まる構図(01・11・18・19・22・main)は0.01〜6.8%で通り、顔アップ(04・12・15・24)は41〜53%で中断した。判定が構図の違いときれいに一致する。

```python
DARK_TH, BRIGHT_TH, LIMIT = 150, 180, 0.08

def shadow_mask(arr):
    alpha = arr[:, :, 3]
    lo = arr[:, :, :3].astype(int).min(axis=-1)
    transparent = alpha < 30
    passable = (lo >= DARK_TH) | transparent      # 濃い輪郭線は通れない
    labeled, _ = ndimage.label(passable)
    border = (set(labeled[0, :]) | set(labeled[-1, :])
              | set(labeled[:, 0]) | set(labeled[:, -1]))
    border.discard(0)
    reached = np.isin(labeled, list(border))
    return reached & ~transparent & (lo > BRIGHT_TH)   # 明るい画素だけ

# 各コマで (消える画素 / 不透明画素) > LIMIT なら、保存せず中断する
```

中断したファイルは、影を消さずに残すこと。

**もう1つの直し方＝コマを切り出す段階(5-4)で落とす。** どちらでもよいが、こちらは作り直しになるので、完成後に気づいたなら上の後処理のほうが速い。次の動画から作るときに影が出ると分かっているなら、最初からこちらを使う。そこでは影はまだ白背景と地続きで、お腹のクリームは濃い輪郭線に囲まれて外周から切り離されている。だから`remove_white_bg()`の判定を「外周と連結した、明るく低彩度の領域」に差し替えれば、影だけが落ちてお腹は残る。base.jpgの足元の影を落とすのと同じ理屈。

```python
def remove_bg_with_shadow(im):
    arr = np.array(im)
    rgb = arr[:, :, :3].astype(int)
    lo = rgb.min(axis=-1)
    bg_like = (lo > 195) & ((rgb.max(axis=-1) - lo) < 45)
    labeled, _ = ndimage.label(bg_like)
    border = (set(labeled[0, :]) | set(labeled[-1, :])
              | set(labeled[:, 0]) | set(labeled[:, -1]))
    border.discard(0)
    alpha = arr[:, :, 3].copy()
    alpha[np.isin(labeled, list(border))] = 0
    arr[:, :, 3] = alpha
    return Image.fromarray(arr, 'RGBA')

# コマ選択・整列・保存は公式のまま使う。
```

**ただしこの差し替えにも構図の制約がある。キャラクターの輪郭が画面内で閉じている構図でだけ使うこと。** 全身が収まっていれば安全(18番で確認)。顔のアップなど体が画面端で切れている構図では、断面で輪郭線が途切れているためそこから浸水し、頬とお腹が消える(15番・24番で確認)。

顔アップで影が残ってしまった場合は、**消さずに残すほうがましだと判断すること**。影はクリーム色に近いので、白や淡色のトーク画面ではほぼ見えない。無理に消そうとすると絵のほうが壊れる。

一番良いのは、そもそも影を描かせないこと。開始ポーズの静止画を描き起こす依頼文と動画生成の依頼文の両方に、「キャラクターの下に影を落とさないこと。背景は完全な白一色にすること」を毎回入れる。

### 3-9. 本体から離れた小さな点が残る。ただし「本体以外を全部消す」は禁物(2026-08-21判明)

動画からコマを抜くと、キャラクターから離れたところに数画素の不透明な点が残ることがある。モーションブラーの名残や、背景除去で取り切れなかった破片。

`check_ghosting()`にも`check_white_fringe()`にも届かず(1コマ60画素のしきい値に遠く及ばない)、白背景でも見えない。彩度の高い背景に置いて初めて分かる。

直し方は「連結成分に分けて、本体以外の小さな島を消す」。ただし**「本体以外を全部消す」と書いてはいけない**。

**体の一部が、輪郭線の細いところで本体と切れて別の島になっていることがある。** ハムスター11番の7コマ目では、高く上げた前足が215画素の独立した島になっていた。全部消す実装だと前足が消える。実際に消える画素を赤く塗った確認画像を作って、初めて気づいた。

**しきい値は60画素**。実測での島の大きさが、次のようにきれいに2群へ分かれるため。

- 体の一部が切れたもの＝215画素(11番の前足)、214画素(24番)
- 本物の点々＝1〜20画素(01・12・15・22・mainと、24番の島269個の大半)

60画素を超える島は体の一部である可能性があるので残し、残した個数を必ずログに出す。残った島が汚れだった場合は、そのスタンプだけ個別に判断する。

```python
MIN_ISLAND = 60

labeled, n = ndimage.label(alpha > 30)
sizes = ndimage.sum(alpha > 30, labeled, range(1, n + 1))
main_label = int(np.argmax(sizes)) + 1
for idx in range(1, n + 1):
    if idx != main_label and sizes[idx - 1] < MIN_ISLAND:
        alpha[labeled == idx] = 0      # 消す
    # 60画素以上の島は残す(体の一部かもしれない)
```

**共通の教訓＝この章の3-7・3-8・3-9はどれも「消しすぎ」で一度ずつ失敗している。** 画素を消す処理を書くときは、(1)何が消えるのかを可視化して目視する、(2)消しすぎたら中断する歯止めを入れる、の2つを必ず先に用意すること。消したあとの画像だけ見ても、消えてはいけないものが消えたことには気づけない。

## 4. 動きを作る前に: まず絵コンテで動作を設計する(ここが一番重要)

最初に「1枚の絵を回転・平行移動させるだけ」の安全な作り方で全部作ってしまい、あとから「体の形が同じまま動かそうとしているから動作していない」と気づいて全部作り直しになった失敗がある。

**この手戻りが一番コストが高い。最初からここを踏むこと**。

### 判定基準: その動きは「回転・平行移動」で正直に表現できるか

1枚の絵を変形させずに動かす技法(回転・平行移動・拡大縮小)は、**その動きが物理的に本当に剛体運動であるときだけ**正直な表現になる。当てはまるのはこの程度。

- 呼吸のような、体全体のわずかな上下(breathing bob)
- その場での回転(目眩・スピン)
- 震え(shiver、小刻みな左右振動)
- しっぽなど、絵から自然に切り離せる部位単体の回転

**それ以外の動き――歩く・手を振る・伸びをする・舐める・跳ねる・転がる・お辞儀する等――は、体のどこかが元の絵と違う形・違う位置を取る必要がある**。これを1枚の絵の回転・平行移動だけで作ると、関節が伸びない/曲がらない/継ぎ目に隙間ができるなど、見た瞬間に不自然だと分かる仕上がりになる。

### 手順

1. **作る予定のポーズ全部を先に一覧にする**。動くスタンプは**24個が基本**なので、最初から24行の一覧表を作る。複数の動きを作るときは、最初に「①=歩く」「②=手を振る」のように動作の一覧表を作ってから着手する(あとから重複や被りに気づいて作り直すのを防ぐ)
2. **開始ポーズ(1コマ目)も全スタンプで変える**。ベース絵1枚を全スタンプの動画生成の参照画像に使い回すと、セット全部が同じ構図から動き出して単調に見える。一覧表には動作の列に加えて「開始ポーズ」の列を作り、寝ている・後ろ姿・完全横向き・顔アップ・しゃがみ・小道具つき(布団・草・温泉)のように、構図と姿勢の段階から全部ばらす。制作は各スタンプ2段構えにする。**まず画像生成モードでベース絵から開始ポーズの静止画を描き起こし、その静止画を動画生成モードの参照画像にして動かす**。ベース絵と同じ構図でよいのはセット全体で1個まで
3. 一覧の動きひとつひとつに、上の判定基準を当てはめる。**「回転・平行移動で正直に表現できる」と自信を持って言えないものは、全部「新しいポーズが要る」側に倒す**。安全そうだからという理由で剛体変換を選ばない
4. 新しいポーズが要ると判定したものは、下の「5. 制作手順」でキーフレームを描き起こしてから、2枚(以上)を切り替えるアニメーションとして組む
5. 剛体変換で足りると判定したものだけ、1枚の絵の回転・平行移動で作る
6. 全部作り終えたら、**「この動きは実際にその動作をしているように見えるか」を1枚ずつ自問する**。「なんとなく動いてはいる」で妥協せず、疑わしいものは4に戻って新しいポーズを足す

## 5. 制作手順(基本方針: 動画を1本作ってコマを抜き出す)

静止画を1枚ずつ描いてもらう方式は、動きの滑らかさが「実際に描いた枚数」止まりで頭打ちになり、生成・ダウンロード・検証のサイクルも多くコストがかかる。

**動画生成モードを使えば、1回の生成依頼で静止画4〜8枚分に相当する滑らかさが手に入る。新規にセットを作るときは、最初からこの動画方式で着手する**。(個別ポーズを1枚だけ直したいときの手段としては、6章の静止画方式を使う)

### 5-1. 参照画像を用意する

4章の絵コンテ手順2の通り、スタンプごとに描き起こした「開始ポーズ」の静止画を用意する。動画の1コマ目はこの参照画像の構図になるため、ここを変えないとセット全部が同じ構図から始まって単調になる。

### 5-2. 動画を生成する

**動画生成AIは、動作名だけを渡すと安全側に倒れて、動きがほとんど分からないくらい小さいアニメーションを作ることが多い。** 「歩くアニメーション」のような依頼文だけでは、実写のような可動域は出ない。**最初の依頼文の時点で、動く部位と、開始状態・終了状態それぞれの具体的な位置を名指しする。** 「動作名を書けば伝わる」と期待しないこと。

1. 画像生成AI(Grok Imagineなど)を開き、参照画像を貼り付ける(アップロード機能、またはクリップボード経由の貼り付け)
2. 「画像」モードから「動画」モードに切り替える
3. 依頼文は次の型で組み立てる。動作名だけで済ませない。

   ```
   このキャラクターの絵柄を一切変えずに、このキャラクターが[動作]するアニメーション。
   [動く部位]を、[開始時の具体的な状態]から[終了時の具体的な状態]まで、
   誰が見てもはっきり分かるくらい大きく動かしてください。
   人間や実際の動物がその動作をするときと同じくらいの、大げさな可動域にしてください。
   背景は白のままで、カメラは固定。
   ```

   例(「手を振る」の場合): 「前足を、体の横に下ろした状態から、頭より高い位置まで大きく振り上げた状態まで、誰が見てもはっきり分かるくらい大きく動かしてください。人間が大きく手を振るときと同じくらいの、大げさな可動域にしてください。」

   例(「歩く」の場合): 「四本の足が交互に、地面についた状態から、体の下から完全に離れて空中に浮いた状態まで、誰が見てもはっきり分かるくらい大きく動かしてください。」

4. 生成が終わるまで待つ(数十秒〜数分。短い間隔で何度も確認する必要はなく、10秒程度の待機を2〜3回で足りる)
5. **生成結果は毎回、動きの大きさを目視確認してから採用する。「一発で十分な大きさが出たらラッキー」くらいに考えて、初回の結果をそのまま採用しない。** 動きが小さい・弱いと感じたら、曖昧な「もっとはっきり動かして」ではなく、具体的な変化量や状態を名指しして再依頼する。「あご先が胸につくくらい」「四本の足全部が地面から完全に離れて体の下に空白ができるように」のように、どこがどこまで動くべきかを言葉にすると一発で決まりやすい
6. 3の依頼文で大げさに指定しても小さい動きしか返ってこない場合は、5の再依頼を最低1回は必ず行う。それでも変わらない場合は、開始ポーズの静止画自体を動きの余地が分かりやすい構図(例: 手を振るなら、最初から片方の前足を軽く浮かせた状態)に描き直してから再生成する

### 5-2-1. 「動かさない部位」を名指しすると崩れが減る。ただし動作を選ぶ(2026-08-21判明)

絵柄が何テイク回しても崩れるとき、**動く部位を絞り、それ以外を名指しで固定する**と通ることがある。ハムスター03番(種をかじって驚く)は4テイク連続で輪郭が細り桃色の縁取りが出ていたが、5テイク目に「動くのは首と頭だけ。胴体・お尻・後ろ足・尻尾は固定」と書いたら無傷になった。

**ただし万能ではない。動作が本当に全身を要するときは、縛るとかえって崩れる。** 同じセットの11番(振り向いて前足を挙げる)では「胴体を動かすな」と縛ったテイクが、チークと尻尾のリス尾化を起こして最も悪い結果になった。振り向きは胴体の回転を伴う動作なので、固定すると無理な姿勢を作ろうとして絵が壊れる。

**使い分け＝その動作が体のどこで完結するかを先に考える。**

- 首から上・前足だけ・しっぽだけで完結する動作(うなずく・かじる・手を振る・しっぽを振る)＝残りを固定と書いてよい。効果が大きい
- 胴体の向きや重心が変わる動作(振り向く・跳ねる・転がる・伸びをする)＝固定と書かない。書くと崩れる

固定を指定して崩れが増えたら、その動作は全身を要する側だったということ。指定を外して、代わりに可動域を少し抑える方向で調整する。

### 5-3. 動画をダウンロードする

- ブラウザのネイティブ「ダウンロード」ボタンは不安定なことが多い(クリックしても保存先に実体が保存されない場合がある)。**「シェア」ボタンから公開リンク(共有URL)を取得し、そのURLを直接`curl`等で取得する方式が確実**。
- 生成結果を採用する前に、ffmpegで2〜3コマ抜き出して目視確認する(共有アカウントを使っている場合、無関係な動画が紛れ込む事故があるため)

```bash
curl -L -o generated.mp4 "<共有経由で取得した動画の直URL>"
ffmpeg -i generated.mp4 -vf "select='eq(n\,0)+eq(n\,30)+eq(n\,60)'" -vsync 0 check_%02d.png
```

### 5-4. 動画からAPNGを作る(スクリプト全文)

以下をそのまま`build_from_video.py`として保存して使う。次の処理をすべて自動で行う。

- 動画を高密度でサンプリングし、フレーム間の動き量(画素差分)を測って、動きが薄い区間を間引き、動いている区間にコマ予算を集中させる(単純に時間で均等抜き出しすると、「間」の区間もコマに含まれ、体感で動きが遅く感じる仕上がりになる。これを避けるための必須ステップ)
- 背景透過(外周と連結した白領域だけをフラッドフィルで透過にする。輪郭内部の白は透過しない)
- 全コマの合成bboxで揃えてクロップ・スケール(270px条件を満たす)
- 隣接コマの重複チェックと自動補正
- 1MBを超えたらフレーム数を20→16→10→8→5の順に自動で下げて保存

```python
#!/usr/bin/env python3
"""動画からLINEスタンプ用APNGを作る(動き量に応じたコマ選択)。

使い方:
    python3 build_from_video.py <動画パス> <出力先NN.png>
"""
import sys
import subprocess
import tempfile
import os
import argparse
import numpy as np
from PIL import Image
from scipy import ndimage


def get_duration(video_path):
    return float(subprocess.run(
        ["ffprobe", "-v", "quiet", "-show_entries", "format=duration",
         "-of", "csv=p=0", video_path], capture_output=True, text=True
    ).stdout.strip())


def extract_dense_frames(video_path, dense_fps, workdir):
    out_pattern = os.path.join(workdir, "dense_%04d.png")
    subprocess.run(
        ["ffmpeg", "-y", "-i", video_path, "-vf", f"fps={dense_fps}", out_pattern],
        check=True, capture_output=True
    )
    files = sorted(f for f in os.listdir(workdir) if f.startswith("dense_"))
    return [os.path.join(workdir, f) for f in files]


def motion_weighted_indices(dense_paths, n_target):
    """密なフレーム列から、動き量の累積が均等になるようにn_target枚選ぶ"""
    grays = [np.asarray(Image.open(p).convert("L")).astype(float) for p in dense_paths]
    diffs = [0.0]
    for i in range(1, len(grays)):
        diffs.append(float(np.abs(grays[i] - grays[i-1]).mean()))
    cum = np.cumsum(diffs)
    if cum[-1] == 0:
        # 動きが検出できない場合は均等割りにフォールバック
        return list(np.linspace(0, len(dense_paths) - 1, n_target).astype(int))
    targets = np.linspace(0, cum[-1], n_target)
    indices = []
    for t in targets:
        idx = int(np.searchsorted(cum, t))
        idx = min(idx, len(dense_paths) - 1)
        indices.append(idx)
    # 重複除去(近すぎる場合は少しずらす)
    for i in range(1, len(indices)):
        if indices[i] <= indices[i-1]:
            indices[i] = min(indices[i-1] + 1, len(dense_paths) - 1)
    return indices


def remove_white_bg(im):
    arr = np.array(im)
    rgb = arr[:, :, :3].astype(int)
    white_mask = np.all(rgb > 240, axis=-1)
    labeled, _ = ndimage.label(white_mask)
    border_labels = set(labeled[0, :]) | set(labeled[-1, :]) | set(labeled[:, 0]) | set(labeled[:, -1])
    border_labels.discard(0)
    bg_mask = np.isin(labeled, list(border_labels))
    alpha = arr[:, :, 3].copy()
    alpha[bg_mask] = 0
    arr[:, :, 3] = alpha
    return Image.fromarray(arr, "RGBA")


def bbox_of(im):
    arr = np.array(im)
    ys, xs = np.where(arr[:, :, 3] > 10)
    if len(xs) == 0:
        return 0, 0, im.width, im.height
    return int(xs.min()), int(ys.min()), int(xs.max()), int(ys.max())


def align_and_crop(frames, pad=20):
    boxes = [bbox_of(f) for f in frames]
    x0 = min(b[0] for b in boxes) - pad
    y0 = min(b[1] for b in boxes) - pad
    x1 = max(b[2] for b in boxes) + pad
    y1 = max(b[3] for b in boxes) + pad
    x0, y0 = max(0, x0), max(0, y0)
    cropped = [f.crop((x0, y0, x1, y1)) for f in frames]
    w, h = cropped[0].size
    scale = min(320 / w, 270 / h)
    new_size = (max(1, int(w * scale)), max(1, int(h * scale)))
    return [f.resize(new_size, Image.LANCZOS) for f in cropped]


def dedupe_adjacent(frames):
    arrs = [np.array(f) for f in frames]
    for i in range(len(arrs) - 1):
        if np.array_equal(arrs[i], arrs[i + 1]):
            arr = arrs[i + 1].copy()
            arr[0, 0, 0] = (int(arr[0, 0, 0]) + 1) % 256
            arrs[i + 1] = arr
            frames[i + 1] = Image.fromarray(arr, "RGBA")
    return frames


def save_sticker(frames, out_path):
    n = len(frames)
    assert n in (5, 8, 10, 16, 20)
    duration = 2000 // n  # デフォルトは2秒(2026-08-20裁定)。ゆったりした動きなら4000にしてもよい
    frames[0].save(out_path, save_all=True, append_images=frames[1:],
                    duration=duration, loop=1, disposal=0, blend=0, compress_level=9)
    return os.path.getsize(out_path)


def build(video_path, out_path, target_frames=None):
    candidates = [target_frames] if target_frames else [20, 16, 10, 8, 5]
    dur = get_duration(video_path)
    dense_fps = 12  # 密なサンプリング(6秒なら約72枚)
    with tempfile.TemporaryDirectory() as workdir:
        dense_paths = extract_dense_frames(video_path, dense_fps, workdir)
        for n in candidates:
            idxs = motion_weighted_indices(dense_paths, n)
            raw_frames = [Image.open(dense_paths[i]).convert("RGBA") for i in idxs]
            clean = [remove_white_bg(f) for f in raw_frames]
            aligned = align_and_crop(clean)
            aligned = dedupe_adjacent(aligned)
            size = save_sticker(aligned, out_path)
            if size <= 1024 * 1024:
                print(f"OK: {n}フレーム(動き量ベース選択), {size/1024:.0f}KB -> {out_path}")
                return n, size
            print(f"{n}フレームは{size/1024:.0f}KBで1MB超過。フレーム数を落とします。")
    raise RuntimeError("5フレームでも1MBを超えました")


if __name__ == "__main__":
    p = argparse.ArgumentParser()
    p.add_argument("video")
    p.add_argument("out")
    p.add_argument("--target-frames", type=int, default=None)
    args = p.parse_args()
    build(args.video, args.out, args.target_frames)
```

実行例:

```bash
python3 build_from_video.py generated.mp4 01.png
```

背景がキャラクター本体の絵柄内にも白い部分がある場合(例: 白目・白い毛)は、`remove_white_bg`が外周と連結した白領域だけを消す設計なので誤って透過しない。ただし念のため、生成前の動画は必ず背景白一色で依頼すること。

**背景透過はこの`remove_white_bg()`で統一し、`rembg`のような汎用の背景除去ツールに差し替えないこと**。汎用ツールに差し替えると、輪郭にごく薄い影(ハロー)が残ることがあり、他のコマや他のスタンプと並べたときに質感だけ浮いて見える。

### 5-5. 「もっと速く」「もっとスムーズに」と言われたときの直し方

**「速い/遅い」と「なめらか/カクつく」は、原因も直し方もまったく別**。混同して片方だけ直しても、もう片方の不満は解決しない。

**「動きが遅い・間延びしている」と言われた場合**: 原因はコマの中身の抽出方法にあることが多い。元動画の中の「ほとんど動いていない間」の区間からも均等にコマを抜いていると、体感で間延びして見える。**対策は5-4の`motion_weighted_indices()`(動き量ベースのコマ抽出)で、このガイドの`build_from_video.py`にはすでに標準搭載されている。** つまり、このスクリプトをそのまま使っている限り、この問題は最初から起きない。もし手元の出力がそれでも間延びして見えるなら、動き量ベースの抽出を素通りする改造(時間で均等に抜く独自コードなど)になっていないか、まずスクリプトの中身を疑うこと。

**「もっと速く/もっとゆっくり(再生時間を変えたい)」と言われた場合**: コマの中身を作り直す必要はない。フレーム数はどれも1000/2000/3000/4000msのすべてを割り切れる(5・8・10・16・20はこの4つ全部を割り切れる)。`save_sticker`関数内の`duration = 2000 // n`(デフォルト)を、速くしたいなら`1000 // n`に、ゆっくりにしたいなら`4000 // n`に変えて保存し直すだけで、同じコマ内容のまま再生速度だけを変えられる。動画の再生成は不要。

実際の制作(ブルドッグ24個セット)では、「動きが遅い」「もっと速く」を順番に指摘されて両方直した実績がある。「動きが遅い」への対応(動き量ベースの抽出への切り替え)を先にやり、そのあとでduration変更をした。**片方をやれば両方解決するわけではない**ので、それぞれ別の要望として扱うこと。

**デフォルトの合計再生時間は2000ms(2秒)**(2026-08-20裁定。以前は4000msが既定だった)。ねこ24個セットの制作で、フレーム数が少ないポーズ(16枚など)を4000msで再生すると「カクカクしている」「速すぎる」と感じられる事故が起きたため、標準を2秒に変更した。既に4000msで作った過去のセット(カピバラ・ブルドッグ・パグ)は、指摘があれば同じ`duration`書き換えだけで2秒版に変換できる(動画の再生成は不要)。

### 5-6. 実写動画からスタンプを作る場合(2026-08-21に確立)

生成AIの絵ではなく、本人が喋っている実写の縦動画(1080x1920・30fps)からスタンプを作るときは、5-4の`build_from_video.py`をそのままは使えない。違いは3つある。

**背景透過は`remove_white_bg()`では抜けない。** 実写の背景は白一色ではないので、フラッドフィルが効かない。代わりに次の2つを掛け合わせる。

1. `rembg`の`bria-rmbg`(RMBG 2.0)でアルファを作る。髪の毛の輪郭まで綺麗に抜ける。CPUで1コマ約8秒
2. Apple Vision の`VNGeneratePersonSegmentationRequest`(qualityLevel=0=accurate)で人物マスクを作る。1コマ0.2秒。**これが「人以外を拾わない」役をする**

1のアルファに2のマスク(10px膨張＋ぼかし)を掛けると、床に転がっているペットボトルのような手前の物体が消えて、手に持っている物と人物だけが残る。1だけだと手前の物も一緒に抜ける。2だけだと輪郭が甘い。この掛け合わせが要点。

`rembg`単体への差し替えを禁じている5-4の注意は、生成AIの絵に対するもの。実写では選択肢がないので、上の組み合わせを使う。

pyobjcの呼び出しは`alloc().init()`も`new()`も`NS_UNAVAILABLE`で落ちる。`VNGeneratePersonSegmentationRequest.alloc().initWithCompletionHandler_(None)`が正解。

**コマの選び方は動き量ベースにしない。** 5-4の`motion_weighted_indices()`は絵の動画向けで、実写の喋り動画に使うと口の動きと発話の速さがずれる。**実尺に対して等間隔に20コマ抜く。** 文字を後から載せる前提なら、なおさら元の話速を崩さないほうがいい。

**再生時間は実尺に一番近い legal な値を選ぶ。** 1000/2000/3000/4000msのうち、実尺との倍率の対数距離が最小のものを取る。1.03秒→1000ms、1.90秒→2000ms、2.83秒→3000msになる。

**1MBの壁は実写だと必ず当たる。** 写真はPNGの圧縮が効かないので、320x270・20コマだと素のままで2〜4MBになる。順番に次を効かせると、20コマを維持したまま800〜980KBに収まる。

1. 完全透明な画素のRGBを黒で揃える(見た目は変わらない。透明部分にも元のRGBが残っていて圧縮を邪魔している)
2. RGBの階調だけを落とす(8bit→7→6→5)。**truecolorのままなのでパレット化にはあたらず、規格の「フルカラー」に反しない。** 実写なら6bitでもほぼ判別できない
3. それでも越えるならコマ数を20→10→5と落とす。**20の約数だけを使う。**16や8にすると間引きが等間隔でなくなり、話速が不均一になる

**寄りにしないと顔が読めない。** 全身のまま270pxに収めると顔が45px程度になる。人物のbboxの上から62%を切り出し、**切ったあとで横幅を測り直す**と(足を広げた分の余白が消えて)顔が2倍近くになる。

**余白は固定pxで取らない。** 元が1080x1920なので、pad=12pxは縮小後に3pxしか残らず帽子の先が枠に貼りつく。**人物bboxの高さの3%**を使う。

**`check_ghosting()`の警告は実写では誤検知が多い。** 透明なペットボトルとモーションブラーで中間アルファが8〜12%になる。7章の但し書きどおり、そのコマが単一の自然なポーズなら無視してよい。

実装は`~/line-sticker-jinbutsu/`の`segment.py`(重い・結果をキャッシュ)と`assemble.py`(軽い・寄りや再生時間の作り直しは数秒)に分けてある。切り抜きをやり直さずに構図だけ変えられるので、この2段構えにしておくこと。

## 6. 静止画方式(1匹の途中経過ポーズを1枚だけ直したいときの補助手段)

新しくポーズを1枚だけ描き起こしたいとき(体の輪郭自体が変わる動き=歩く・手を振る・伸びをする等)は、この手順を使う。

1. 元の絵を画像生成AIに画像として渡す
2. 「この画像とまったく同じ絵柄・線の太さ・配色・同じキャラクターの、[動作]を、[変えたい部分だけを具体的に]変えたポーズだけ新しく1枚描いてください」と指定する
   - 悪い例:「手を振っているポーズを描いて」(絵柄がズレやすい)
   - 良い例:「今の画像は右前足を高く上げています。新しい絵ではその前足を下ろして、体の横あたりの低い位置にしてください」(変える部位を名指しする方が一発で決まりやすい)
3. 背景は白一色、スタイルは元画像と完全に同じに揃えるよう毎回明記する
4. 出力を元の絵の足元位置(接地面)に合わせて拡大縮小・位置合わせしてから、2枚(以上)を切り替えるアニメーションとして組む
5. 生成が一発で決まらないときは、「まだ○○のままです。○○を完全に△△にしてください」と、変わっていない部分を名指しして再依頼する(曖昧な「もっとはっきり」だと変化が小さいまま終わることがある)

**静止画のダウンロードも、ブラウザのネイティブ「ダウンロード」ボタンは不安定(クリックしても実体が保存されないことがある)**。生成画像の「共有」ボタンから公開リンクを取得し、それを直接`curl`で取得する方式が確実。Grokの場合は共有リンクが`https://pbs.twimg.com/grok-img-share/{mediaId}.jpg`のような形式になる。

```bash
curl -L -o pose_02.jpg "<共有ボタンから取得した公開URL>"
```

ダウンロード後は必ず画像を開いて中身と解像度を確認する。共有アカウントを使っている場合、無関係な画像が紛れ込む事故があるため、低解像度・別の絵柄のまま採用しない。

## 7. コマ数を増やしたいとき、アルファブレンド(クロスフェード)は絶対に使わない

「動きが荒い・コマ送りに見える」という理由でコマ数を増やしたくなっても、**絵柄の違う2枚のポーズ画像を単純にアルファブレンド(クロスフェード)で混ぜて中間コマを作ってはいけない**。2つの絵の輪郭がずれて重なった部分が透けて見える「残像(ゴースト、二重写り)」になる。1枚の絵柄が別の絵柄に溶けて重なった状態は、実際にはどちらのポーズにもなっていない、誰が見てもおかしいと分かる仕上がりになる。

コマ数を増やしたいときは、**実際に別の中間ポーズを画像生成AIに描き起こしてもらい、硬い切り替え(ブレンドなし)だけでコマを構成する**。絵コンテ設計のときと同じで、「行って戻る」動きなら中間ポーズを1枚足してA,B,C,B,Aのように、実在するポーズ同士を切り替える。

動画由来のコマは、線画の抜き出しと違ってわずかな動きブレが乗ることがある。次章のチェックにごく僅差でひっかかることがあるが、該当フレームを目視して、二重写りでなく単一の自然なポーズであれば、誤検知として扱ってよい。

## 8. 保存前チェック(そのまま使える。全チェックが空リストになってから次へ進む)

```python
from PIL import Image
import numpy as np
import os


def validate_line_sticker(path, is_main=False):
    """規格チェック。空リストが返れば規格クリア。"""
    im = Image.open(path)
    n = im.n_frames if getattr(im, 'is_animated', False) else 1
    frames, durs = [], []
    for i in range(n):
        im.seek(i)
        frames.append(np.asarray(im.convert('RGBA')))
        durs.append(im.info.get('duration', 0))
    total = sum(durs)
    w, h = im.size
    maxw, maxh = (240, 240) if is_main else (320, 270)

    problems = []
    if not (w <= maxw and h <= maxh):
        problems.append(f'サイズ超過 {w}x{h}')
    if not is_main and not (w >= 270 or h >= 270):
        problems.append(f'縦横どちらも270px未満 {w}x{h}')
    if not is_main and not (5 <= n <= 20):
        problems.append(f'フレーム数が範囲外 {n}')
    if total not in (1000, 2000, 3000, 4000):
        problems.append(f'再生時間が1/2/3/4秒ぴったりでない {total}ms')
    if len(set(durs)) > 1:
        problems.append(f'コマの長さが不揃い {durs}')
    for i in range(len(frames) - 1):
        if np.array_equal(frames[i], frames[i + 1]):
            problems.append(f'隣接フレーム{i},{i+1}が同一(保存時に統合される)')
    kb = os.path.getsize(path) / 1024
    if kb > 1024:
        problems.append(f'ファイルサイズ超過 {kb:.0f}KB')
    return problems


def check_ghosting(path, threshold=0.08):
    """残像(クロスフェードの混ざり)の疑いを検出する。
    非透明ピクセルのうち、中間アルファ値(25〜230)を持つピクセルの比率が
    しきい値を超えたら警告する。"""
    im = Image.open(path)
    n = im.n_frames if getattr(im, 'is_animated', False) else 1
    warnings = []
    for i in range(n):
        im.seek(i)
        arr = np.asarray(im.convert('RGBA'))
        alpha = arr[:, :, 3]
        opaque = int(np.sum(alpha > 230))
        mid = int(np.sum((alpha >= 25) & (alpha <= 230)))
        if opaque > 0 and mid / opaque > threshold:
            warnings.append(f'フレーム{i}: 中間アルファ比率{mid/opaque:.1%}(残像の疑い。目視で確認)')
    return warnings


# 使い方:
# validate_line_sticker('01.png')  が空リストを返せば規格クリア
# validate_line_sticker('main.png', is_main=True)  メイン画像用
# check_ghosting('01.png')  空リスト、または目視確認して問題なければ無視してよい
```

### 8-1. 保存コード(1枚の絵を回転・平行移動だけで作る場合)

4章の判定基準で「剛体変換で足りる」と判定した動き(呼吸・回転・震え・しっぽ単体の回転など)は、動画生成を経由せず、コードで直接フレームを作ってよい。保存時は次の関数をそのまま使う。

```python
def save_line_sticker(frames, path, loop=1):
    """frames: 同じ長さのPIL RGBA Imageのリスト。
    長さは合計再生時間(デフォルト2000ms)を割り切れる数(5・8・10・16・20)にすること。"""
    n = len(frames)
    assert n in (5, 8, 10, 16, 20), f'フレーム数{n}は2000msを割り切れない。5/8/10/16/20枚にする'
    duration = 2000 // n  # デフォルトは2秒(2026-08-20裁定)。ゆったりした動きなら4000にしてもよい
    frames[0].save(path, save_all=True, append_images=frames[1:],
                    duration=duration, loop=loop, disposal=0, blend=0, compress_level=9)
```

フレームを作る側(回転角度やずらす距離を計算する部分)は動きの内容によって変わるので、ここでは共通化していない。作ったフレームの並びは保存前に必ず8章の`validate_line_sticker()`と`check_ghosting()`を通す。

1枚(main.png、tab.pngを含む全ファイル)ずつ`validate_line_sticker()`を実行し、空リストになることを確認してから次に進む。`tab.png`は静止画(96×74)なので、このチェック対象には含めなくてよい。サイズだけ手動で確認する。

## 10. 複数キャラクター・複数ポーズを並行して作るときの注意

- 複数の作業(複数キャラクター、複数ポーズ)を同時並行で進めると、同じ画像生成アカウント・同じダウンロードフォルダを取り違える事故がほぼ毎回起きる。**ダウンロード直後に画像の中身と解像度を必ず確認してから採用する**ことを毎回徹底する
- **ブラウザのタブは担当ごとに新規に作り、既存のタブを流用しない(2026-08-21判明)。** 既存タブを流用したところ、そのタブを別の担当が使っていて、添付画像が2枚並ぶ事故が起きた。生成前に気づいたので実害は出なかったが、気づかなければ相手の生成に自分の画像が混入していた
- **クリップボードを使わずに参照画像を渡す方法があり、並行作業をするならこちらを使う(2026-08-21判明)。** クリップボードもダウンロードフォルダも共有資源なので、衝突を避ける一番確実な手はどちらも経由しないこと。ブラウザ内でJavaScriptを実行できる環境なら、次の経路が通る。

  1. 画像のバイト列を **hex文字列** にしてページ内のJavaScriptへ渡す。base64はツール側にブロックされることがある
  2. ページ内でBlobに戻し、canvasを経由してJPEGの`File`オブジェクトを作る
  3. `input[type=file]`の`files`にセットしてchangeイベントを発火する

  生成物の取得も同じ考え方で、`fetch(<生成物のURL>, {credentials:'include'})`でblobを取り、`<a download>`を`click()`する。`curl`は認証クッキーが乗らず0バイトのファイルになることがある。

  なお、この経路が要るのは並行作業をしている場合。1件ずつ順番に作るならクリップボードで問題ない。

- **参照画像の受け渡しにOSのクリップボードを使う場合、並行作業がクリップボードを上書きする(2026-08-21判明)。** クリップボードはマシン全体で1つしかない共有資源なので、3件を並行させると必ず衝突する。ハムスターセットの制作中に、別の作業が上書きした結果、画像を貼るはずの入力欄に無関係なリンクが貼り込まれる事故が起きた。対策は、(1)貼り付ける直前にコピーし直す(コピーしてから時間を空けない)、(2)貼り付けた後に入力欄のサムネイルを目視して意図した画像が付いていることを確認してから生成ボタンを押す、の2つ。生成を走らせてから気づくと1回分が丸ごと無駄になる
- 画像生成AIの1日の生成上限に達することがある。ChatGPTが使えなければGrok、Grokが使えなければChatGPTのように、同等品質の代替を使ってよい(絵柄再現の精度は同程度)
- 新しいポーズの描き起こしは、並列化してもアカウント上限やタブ混線で早々に止まりやすく、効果が薄い作業だと割り切る。並列で試して事故が増えるようなら、早めに1つずつの逐次処理に切り替える
- ダウンロード後は解像度が元画像(1000px級)相当あることを必ず確認し、小さければ失敗として取得し直す。低解像度のまま妥協しない
- **生成→ダウンロード→確認のサイクルを、最初から最後まで同じ会話スレッド(コンテキスト)の中だけで回さない。** 8個のポーズだけの試作でも、生成の待ち時間・スクリーンショット確認・やり直しのやり取りを1つの会話に貯め続けると、1000往復を超えることがある(実例: 8個の試作だけで1125メッセージに達し、コンテキストを大量に消費したケースを確認している)。使っているツールがサブタスク・別プロセス・別エージェントへの作業委譲をサポートしている場合は、1ポーズ(または数ポーズ)ごとに独立した実行単位へ切り出し、本体側は方針決定と完成品の検収だけを行う設計にする。委譲の手段が無い場合でも、生成のたびに会話を区切る・不要になった中間ファイルやスクリーンショットの内容を会話に貼り続けないなど、1つの会話に全工程を溜め込まない工夫をする

## 11. この手順でできないこと(人間が行う部分)

`creator.line.me` はブラウザ自動化ツールから安全上の制限で直接操作できない場合がある。その場合は次を人間が行う。

- LINE Creators Marketへの実際のログイン・画像アップロード・「審査をリクエスト」ボタンのクリック
- できるのは「規格に通るファイル一式(ZIP・個別APNG・main・tab)を作って渡す」ところまで

アップロード後にエラーが出た場合は、**赤い「Error」バッジをクリックして出てくる具体的なメッセージを必ず確認する**。「Error」としか表示されていない段階では原因を特定できないので、憶測で直さない。

## 12. 作業の通し手順(まとめ)

1. 作るポーズ全部を一覧表にする(動作・開始ポーズの列を必ず作る。4章参照)
2. 各ポーズについて「回転・平行移動で足りるか、新しいポーズが要るか」を判定する
3. 新しいポーズが要るものは、開始ポーズの静止画を作ってから動画生成→`build_from_video.py`でAPNG化(5章)
4. 剛体変換で足りるものは、1枚の絵をコードで回転・平行移動させてAPNG化する(3章の対策を踏まえて`save_sticker`相当の関数で保存)
5. 全ファイルに`validate_line_sticker()`と`check_ghosting()`を実行し、問題ゼロを確認する
6. `main.png`(240×240、アニメーション)と`tab.png`(96×74、静止画)を作る
7. `01.png`〜`NN.png`+`main.png`+`tab.png`をフラットにzip化する
8. zipをユーザーに渡し、LINE Creators Marketへのアップロードと審査リクエストはユーザー自身に行ってもらう
